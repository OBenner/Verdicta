# Verdicta — проектная спецификация

- **Дата:** 2026-11-09
- **Статус:** согласованная архитектура, ожидает ревью пользователя
- **Лицензия проекта:** Apache-2.0
- **Слоган:** «Делегируй код. Получай доказательства»

## 1. Краткое описание

Verdicta — независимый local-first control plane для делегирования задач сторонним coding-агентам. Он не является форком Auto-Claude, не реализует собственный coding-агент и не конкурирует с моделями или CLI-агентами в качестве исполнителя кода.

Пользователь описывает задачу и критерии приёмки. Verdicta создаёт отдельный `git worktree`, запускает выбранный внешний агент в Docker, наблюдает за выполнением, запрашивает необходимые разрешения, затем самостоятельно повторяет обязательные проверки и формирует воспроизводимый пакет доказательств.

Основной результат запуска:

```text
ChangeSet + EvidenceBundle + Verdict
```

Заявление агента «готово» не является доказательством. Успешное завершение процесса агента, зелёный статус в пользовательском интерфейсе и успешная проверка результата — разные события.

## 2. Проблема

Coding-агенты умеют самостоятельно планировать шаги, изменять файлы, вызывать инструменты и запускать тесты. При параллельной или автономной работе пользователю всё равно приходится отвечать за:

- постановку проверяемой задачи;
- изоляцию изменений и процессов;
- контроль доступа к секретам, сети и опасным операциям;
- восстановление после зависания, перезапуска или отмены;
- независимую проверку результата;
- сохранение доказательств того, что именно было выполнено;
- различие между техническим сбоем, неуспешной проверкой и необходимостью решения человека.

Verdicta выносит эти функции в отдельный слой управления, не дублируя внутреннюю микрооркестрацию coding-агента.

## 3. Цели

1. Работать с существующими Codex, Claude Code, Kimi Code, OpenCode и другими агентами через расширяемые адаптеры.
2. Не требовать model API key для ядра и локального интерфейса.
3. Давать агенту законченный контракт задачи, а не управлять каждой его командой.
4. Изолировать каждую попытку на уровне Git и на уровне процесса.
5. Независимо повторять обязательные проверки после завершения работы агента.
6. Вычислять итоговый вердикт детерминированными правилами.
7. Сохранять достаточно доказательств для локального аудита и воспроизведения.
8. Предоставлять CLI и Web UI как равноправные клиенты одного локального API.
9. Корректно обрабатывать отмену, тайм-аут, исчерпание лимитов и перезапуск сервиса.
10. Не изменять основную ветку и не выполнять push или merge автоматически.

## 4. Не входит в MVP

- Собственный coding-агент, planner-LLM или ролевые цепочки Planner/Coder/QA.
- Прямые вызовы моделей в основном сценарии.
- Автоматический merge, push, публикация PR или изменение защищённых веток.
- Граф задач с зависимостями и автоматическая декомпозиция крупных проектов.
- Electron или Tauri.
- Облачная мультитенантность, командные аккаунты и удалённое управление.
- Графовая память и автоматическое долговременное обучение.
- LLM-review как обязательный этап или источник окончательного вердикта.
- Отдельные IDE-расширения.
- Криптографически подписанные attestations и удалённая нотариализация evidence.
- Гарантия безопасности против скомпрометированного Docker daemon, ядра ОС или администратора машины.

Эти возможности могут появиться позже как отдельные проекты или расширения, но не должны влиять на стабильность доменных контрактов MVP.

## 5. Основные принципы

### 5.1 Микрооркестрация остаётся в агенте

Агент самостоятельно выбирает последовательность чтения файлов, редактирования, вызова инструментов и локальных проверок. Verdicta не пытается превратить его в набор удалённых функций.

### 5.2 Макрооркестрация принадлежит Verdicta

Verdicta управляет контрактом, ресурсами, изоляцией, разрешениями, попытками, repair-rounds, независимой проверкой и окончательным решением.

### 5.3 Проверяются артефакты, а не уверенность агента

Источниками результата служат реальный diff, коммиты, коды завершения независимо запущенных команд, машинные отчёты тестов и зафиксированные ограничения. Сводка агента сохраняется как неподтверждённый комментарий.

### 5.4 Fail closed для обязательных проверок

Отсутствующий отчёт, нечитаемый результат, истёкший тайм-аут, неизвестный статус команды или повреждение evidence не могут считаться успехом.

### 5.5 Один доменный API, несколько интерфейсов

CLI, Web UI, MCP и будущий Agent Plugin вызывают один application service. Они не содержат собственных версий state machine, правил вердикта или записи в хранилище.

### 5.6 Адаптеры не определяют домен

Типы ACP, MCP, Vercel AI SDK, Workflow SDK и конкретного vendor SDK не попадают в `TaskContract`, `Run`, `ChangeSet`, `EvidenceBundle` или `Verdict`.

## 6. Архитектура

```text
┌──────────────┐  ┌──────────────┐  ┌──────────────────┐
│     CLI      │  │ Local Web UI │  │ MCP / Agent Plugin│
└──────┬───────┘  └──────┬───────┘  └────────┬─────────┘
       └─────────────────┼───────────────────┘
                         │ local HTTP API + SSE
                ┌────────▼─────────┐
                │ Application Core │
                │ tasks, runs,     │
                │ approvals, policy│
                └───────┬──────────┘
                        │
       ┌────────────────┼───────────────────┐
       │                │                   │
┌──────▼──────┐  ┌──────▼───────┐  ┌────────▼────────┐
│ SQLite +    │  │ Run          │  │ Evidence +      │
│ content-    │  │ coordinator  │  │ independent     │
│ addressed   │  │ and recovery │  │ verifier        │
│ artifacts   │  └──────┬───────┘  └─────────────────┘
└─────────────┘         │
              ┌─────────┼──────────┐
              │         │          │
       ┌──────▼────┐ ┌──▼───────┐ ┌▼───────────────┐
       │ Git       │ │ Docker   │ │ AgentRuntime   │
       │ worktrees │ │ workers  │ │ adapters       │
       └───────────┘ └────┬─────┘ │ ACP/native/CLI │
                          │       └───────┬────────┘
                          └───────────────┘
                                  │
                         external coding agent
```

### 6.1 Local service

Постоянный локальный процесс владеет очередью, состоянием, координацией и evidence. По умолчанию HTTP API доступен только на loopback. События передаются клиентам через SSE; изменяющие операции выполняются через HTTP API.

В MVP удалённое прослушивание сетевых интерфейсов запрещено. Это исключает необходимость преждевременно проектировать аутентификацию и удалённую авторизацию.

### 6.2 Run coordinator

Координатор — единственный компонент, который изменяет технический статус запуска. Переходы выполняются транзакционно и используют lease с владельцем и сроком действия. Планировщик не полагается только на системные часы или живость процесса без сверки с реальными Docker/worktree-идентификаторами.

По умолчанию выполняется один активный запуск на установку Verdicta; остальные стоят в очереди. Локальный оператор может увеличить лимит после явной настройки ресурсов.

### 6.3 AgentRuntime

`AgentRuntime` — собственный стабильный порт между ядром и внешним агентом. Концептуальные операции:

```text
probe
prepareAuthentication
start
sendInstruction
resolveApproval
cancel
resume
streamEvents
inspectSession
```

Адаптер публикует capabilities: интерактивные follow-ups, approvals, resume, structured events, usage limits, MCP configuration и supported authentication modes. Отсутствие возможности не маскируется: ядро либо выбирает поддерживаемый сценарий, либо блокирует запуск с объяснением.

Поддерживаемые типы адаптеров:

1. **ACP** — предпочтителен, когда агент реализует нужные возможности протокола.
2. **Native SDK** — используется, если официальный SDK даёт более полный контроль, но остаётся внутри адаптера.
3. **Headless CLI** — базовый вариант с зафиксированной версией CLI, структурированным выводом и contract tests.

ACP не является обязательной зависимостью. Headless CLI не означает разбор человекочитаемого текста регулярными выражениями, когда доступен машинный формат.

### 6.4 MCP

MCP применяется для доступа агента к знаниям и внешним инструментам: WeKnora, GitHub, Linear и другим явно разрешённым сервисам. Он не является основным каналом запуска, приостановки, возобновления и отмены coding-агента.

Отдельный MCP server Verdicta — это клиентская поверхность к ядру: создать задачу, получить статус, прочитать evidence, запросить или подтвердить разрешение. Он не заменяет `AgentRuntime`.

### 6.5 Независимый verifier

Verifier получает зафиксированный `TaskContract`, конкретный `ChangeSet` и отдельный чистый контекст выполнения. Он не принимает от агента флаг успеха и не использует его сводку как условие перехода.

Обязательные команды запускаются повторно уже после завершения агента. Используются заранее объявленные коды выхода, тайм-ауты и, где доступно, машинные test reports. Verifier и policy engine выполняются вне контроля агента; agent-writable workspace не может изменить правила проверки текущего запуска.

## 7. Доменная модель

### 7.1 TaskContract

Неизменяемая версированная спецификация работы:

- `id`, `schemaVersion` и хэш содержимого;
- цель и контекст;
- репозиторий и точный `baseRevision`;
- acceptance criteria;
- обязательные команды проверки и их тайм-ауты;
- допустимые пути и явно запрещённые изменения;
- политика изменений: `required`, `allowed` или `forbidden`;
- ограничения сети, секретов, MCP и инструментов;
- лимиты времени, памяти, CPU, PID, попыток и repair-rounds;
- delivery rules: создать локальную ветку и сохранить результат без merge/push;
- требования к ручным approvals;
- классификация данных и правила удержания evidence.

Любое изменение после запуска создаёт новую версию контракта. Старые попытки всегда ссылаются на исходную версию.

### 7.2 Run

Техническое выполнение конкретного контракта:

- выбранные runtime и версии адаптера/агента;
- workspace, branch, container и session identifiers;
- текущий lease;
- попытки и repair-rounds;
- счётчики использования ресурсов, если runtime их предоставляет;
- временные метки и причина терминального состояния;
- ссылка на итоговые `ChangeSet`, `EvidenceBundle` и `Verdict`.

### 7.3 Attempt и RepairRound

`Attempt` — технический запуск runtime, включая неудачный старт или обрыв. `RepairRound` — новая работа агента над тем же изменением после независимой проверки.

Инфраструктурный retry не скрывается внутри попытки. Каждый retry и repair получает отдельный номер, логи и причину. Число попыток нельзя представлять пользователю как число успешных независимых решений.

### 7.4 ChangeSet

- репозиторий, base revision и итоговый head commit;
- локальная ветка;
- список коммитов;
- полный diff и его хэш;
- changed files;
- untracked/binary-изменения;
- признаки нарушения path policy;
- ссылка на сохранённый worktree.

Пустой diff допустим только при `changePolicy=allowed` или `forbidden`. При `required` пустой diff всегда даёт `failed`; при `forbidden` любой diff даёт `failed`.

### 7.5 EvidenceBundle

Версионированный пакет, содержащий:

- `TaskContract` и его хэш;
- base/head revisions и полный diff;
- версии Verdicta, адаптера, агента и Docker image digest;
- разрешённое описание окружения без значений секретов;
- все независимо выполненные команды, коды выхода и длительность;
- stdout/stderr как отдельные артефакты;
- машинные отчёты тестов, если формат поддерживается;
- события approvals и отмен;
- попытки, retries и repair-rounds;
- результаты policy rules;
- сводку агента с пометкой `unverified`;
- список `limitations`;
- manifest с SHA-256 каждого артефакта.

После финализации bundle неизменяем. Исправление результата создаёт новый bundle, связанный с предыдущим. JSONL допускается как экспорт событий, но не как основной механизм транзакционного состояния.

### 7.6 Verdict

Возможные значения:

- `passed` — все обязательные проверки и approvals завершены, ограничений, препятствующих приёмке, нет;
- `needs_review` — техническая проверка завершена, но есть неавтоматизируемые критерии, warnings или существенные limitations;
- `blocked` — выполнение остановлено политикой, отсутствующим разрешением или внешней зависимостью;
- `failed` — обязательная проверка не пройдена, результат нарушает контракт либо исчерпаны разрешённые repair-rounds.

`passed` означает только прохождение машинных gates Verdicta и не означает разрешение на merge.

## 8. Жизненный цикл

### 8.1 Технические статусы Run

```text
queued → preparing → running → verifying → completed
                    │   ▲          │
                    │   └ repairing┘
                    ▼
             awaiting_approval

queued/preparing/running/awaiting_approval/verifying/repairing → cancelling → cancelled
queued/preparing/running/awaiting_approval/verifying/repairing → failed
awaiting_approval → running
```

- `completed` означает, что pipeline дошёл до решения и обязан иметь `Verdict`, включая `failed` или `blocked`.
- `failed` у `Run` означает инфраструктурный сбой без достоверного итогового вердикта. UI явно показывает «ошибка выполнения», а не «тесты не прошли».
- `cancelled` сохраняет все доступные артефакты и не приравнивается к успеху или неуспеху кода.
- `awaiting_approval` возвращается в `running` только после действительного разрешения либо после отказа, если контракт позволяет агенту продолжить без запрещённой операции.

### 8.2 Основной сценарий

1. Пользователь создаёт задачу через CLI или Web UI.
2. Ядро валидирует репозиторий, base revision, проверки, runtime и Docker.
3. Контракт фиксируется; создаётся ветка и отдельный worktree.
4. SecretProvider готовит минимальные ephemeral credentials.
5. Docker worker запускается с ограничениями ресурсов и выбранной сетевой политикой.
6. Адаптер передаёт агенту `TaskContract` и разрешённый контекст.
7. События и запросы approvals сохраняются; опасные операции требуют решения пользователя.
8. После завершения агента фиксируется `ChangeSet`.
9. Verdicta повторяет обязательные проверки и оценивает правила.
10. При допустимом repair-round агент получает структурированные замечания и повторяет работу.
11. Итоговые артефакты финализируются; ветка и worktree сохраняются для человека.

### 8.3 Approvals

Approval привязан к запуску, конкретному действию, хэшу параметров и сроку действия. Изменение команды, пути, сетевого назначения или секрета требует нового решения. Разрешение «всегда» в MVP не поддерживается.

Если операция обязательна для продолжения, отказ завершает Run со статусом `completed` и вердиктом `blocked`. Если контракт позволяет продолжить без неё, агент получает отказ и Run возвращается в `running`. Истёкший approval не исполняется.

### 8.4 Retry, resume и cancel

- Автоматический retry разрешён только для классифицированных временных инфраструктурных ошибок.
- Неопределённый результат операции с внешними побочными эффектами не повторяется автоматически.
- Repair-round получает предыдущий verifier feedback, но не может превысить бюджет контракта.
- Resume использует сохранённую agent session только если адаптер подтверждает идентичность session, worktree, branch и base revision.
- Если идентичность подтвердить нельзя, создаётся новая попытка с явным человеческим решением; старая не объявляется успешной.
- Cancel сначала запрашивает graceful stop, затем после настраиваемого grace period останавливает контейнер. Логи, diff и причина отмены сохраняются.

## 9. Изоляция и безопасность

### 9.1 Границы доверия

Доверенными считаются локальный оператор, ядро Verdicta, SQLite/artifact store и Docker daemon. Недоверенными считаются:

- код и инструкции в проверяемом репозитории;
- вывод агента и содержимое логов;
- зависимости, загружаемые проектом;
- внешние MCP servers;
- содержимое issue, документов и других источников контекста.

Внешний текст — данные, а не инструкции для policy engine или verifier.

### 9.2 Worktree не является sandbox

Worktree изолирует Git-изменения, но не мешает процессу читать host filesystem, сеть или другие worktree. Поэтому агент и команды проверки выполняются в Docker.

Базовые ограничения worker:

- non-root user;
- read-only root filesystem и отдельные writable mounts;
- `cap_drop=ALL`;
- запрет Docker socket и широкого монтирования host home;
- лимиты CPU, памяти, PID и времени;
- только явно выбранный worktree и минимальные credential mounts;
- отсутствие наследования полного host environment;
- отдельный container identity для каждой попытки.

Отсутствие Docker — блокирующая ошибка `doctor`, а не повод незаметно перейти к исполнению на host.

### 9.3 Сеть

Поддерживаются профили:

- `none` — сеть отключена;
- `allowlist` — исходящий трафик только к явно разрешённым provider/package/MCP endpoints через egress policy;
- `full` — разрешён весь исходящий трафик и требует отдельного approval при создании запуска.

По умолчанию используется `allowlist`. Правила фиксируются в evidence. Verdicta не обещает защиту от DNS/tunneling при выборе `full` и явно показывает ослабление границы.

### 9.4 Секреты и аутентификация

В основном сценарии ядро не имеет model API key. Агент использует собственный CLI/OAuth login. Адаптер через `SecretProvider` может подготовить ограниченные ephemeral credentials для конкретного worker.

Правила:

- не монтировать весь host home;
- не записывать секреты в SQLite, task text, logs, diff metadata или EvidenceBundle;
- передавать только необходимые credential material и только на время запуска;
- не сохранять environment values в evidence;
- скрывать значения секретов в UI и API;
- применять redaction к известным секретам и типовым форматам токенов;
- считать redaction защитой от случайной утечки, а не доказательством невозможности утечки через произвольный вывод;
- удалять ephemeral credential material при очистке worker.

Если CLI login нельзя безопасно перенести в worker, пользователь может явно предоставить agent API key через OS keychain или одноразовый environment input. Это credentials агента, а не ключ ядра.

### 9.5 Логи и prompt injection

Логи экранируются как данные в Web UI и не интерпретируются как HTML или Markdown с активным содержимым. Внешние инструкции не могут изменить `TaskContract`, verifier commands или policy. Для изменения этих объектов требуется локальное действие пользователя.

## 10. Хранение

### 10.1 SQLite

SQLite — источник истины для:

- задач и версий контрактов;
- запусков, попыток и leases;
- approvals;
- runtime/session identifiers;
- индексов артефактов;
- итоговых verdicts.

Записи о переходе состояния и связанном событии выполняются атомарно. Миграции версионируются и тестируются на восстановление из предыдущей схемы.

### 10.2 Artifact store

Большие логи, diffs, reports и manifests хранятся как файлы с SHA-256. SQLite содержит относительный путь, размер, MIME type и хэш, но не дублирует всё содержимое.

Пути внутри store не зависят от расположения пользовательского репозитория. Bundle можно перемещать и проверять офлайн. Удаление evidence выполняется только явной командой retention/cleanup и не удаляет ветку пользователя.

### 10.3 Восстановление

При старте сервис reconciler:

1. находит leases с истёкшим владельцем;
2. сверяет записи с реальными containers, sessions и worktrees;
3. не запускает дубликат, пока судьба предыдущей попытки неизвестна;
4. помечает неподтверждённое состояние как требующее решения;
5. возобновляет только безопасные идемпотентные операции;
6. сохраняет все расхождения в recovery events.

## 11. Правила вычисления Verdict

Порядок применения правил фиксирован:

1. Если policy запрещает выполнение либо обязательное approval отклонено или отсутствует — `blocked`.
2. Если обязательная команда не запущена, завершилась ошибкой, превысила timeout или дала нечитаемый обязательный отчёт — `failed`.
3. Если изменены запрещённые пути, отсутствует обязательный diff либо присутствует diff при `changePolicy=forbidden` — `failed`.
4. Если остались неавтоматизируемые acceptance criteria, warnings или существенные limitations — `needs_review`.
5. Только после прохождения предыдущих правил — `passed`.

Правила применяются к полному набору результатов: любой `blocked` или `failed` с более высоким приоритетом не может быть скрыт последующим успешным правилом. Инфраструктурная невозможность получить достоверный результат завершает Run техническим `failed`, а не вердиктом о качестве кода.

LLM-review может добавить finding или рекомендацию `needs_review`, но не может:

- превратить упавший обязательный тест в `passed`;
- отменить нарушение policy;
- подтвердить отсутствующий approval;
- заменить независимое выполнение команды.

## 12. Пользовательские поверхности

### 12.1 CLI

Базовые команды:

```text
verdicta serve
verdicta doctor
verdicta run
verdicta status
verdicta logs
verdicta evidence
verdicta approve
verdicta deny
verdicta cancel
verdicta resume
```

CLI поддерживает человекочитаемый и JSON output. Коды выхода различают usage error, infrastructure failure, policy refusal и неуспешный verifier result. CLI не записывает состояние напрямую в SQLite.

### 12.2 Web UI

MVP содержит:

- список задач и запусков;
- форму создания `TaskContract`;
- живой статус и поток событий;
- очередь approvals;
- diff и changed files;
- результаты проверок;
- просмотр EvidenceBundle и limitations;
- действия cancel/resume/repair в пределах контракта.

UI не подписывает статус «done» по сообщению агента. Технический статус и `Verdict` визуально различны.

### 12.3 MCP и Agent Plugin

В MVP агент может использовать внешние MCP servers для знаний и инструментов. Собственный MCP server Verdicta с read/approval/task операциями и Agent Plugin из Skill + MCP configuration добавляются после MVP как тонкие клиенты того же API.

Не предполагается существование одного универсального бинарного плагина для всех IDE и агентов. Универсальным является API ядра; каждый клиент получает небольшой адаптер под свою модель расширений.

## 13. Технологические решения

- **Язык:** TypeScript.
- **Runtime сервиса:** Node.js 24.
- **Монорепозиторий:** pnpm workspace.
- **Web UI:** React + Vite.
- **Хранение:** SQLite + content-addressed files.
- **События UI:** SSE.
- **Изоляция:** Docker workers.
- **Git:** отдельный worktree и ветка на запуск.
- **Лицензия:** Apache-2.0.

Предварительные границы модулей:

```text
apps/cli

apps/web

packages/application
packages/storage
packages/git-workspace
packages/sandbox
packages/runtime

packages/evidence

```

Vercel AI SDK допустим в будущих model-backed расширениях, а Workflow SDK — в отдельной реализации orchestration port. Они не требуются для MVP и не должны определять доменные типы. Ядро сохраняет возможность работать без сетевых сервисов Vercel и без собственного model provider.

## 14. Объём MVP

MVP включает:

- один локальный оператор и один репозиторий на задачу;
- очередь независимых задач без dependency graph;
- application API, CLI и Web UI;
- `AgentRuntime` с ACP и headless CLI адаптерами;
- reference-профили минимум для двух внешних агентов: Codex и Claude Code;
- совместимость Kimi Code через ACP только после прохождения общего adapter contract suite;
- Docker и git worktree для каждой попытки;
- scoped secrets и network profiles;
- approvals, limits, retry, repair, cancel и crash recovery;
- независимый verifier и детерминированный `Verdict`;
- SQLite, EvidenceBundle и офлайн-проверку хэшей;
- WeKnora как опциональный MCP knowledge source без переноса его модулей в Verdicta.

Поддержка OpenCode и других агентов достигается через тот же порт, но объявляется только после фактического прохождения compatibility tests, а не по наличию одноимённого адаптера.

## 15. Критерии приёмки MVP

### 15.1 Успешный E2E

На fixture-репозитории с воспроизводимой ошибкой внешний агент создаёт исправление в отдельной ветке. Verdicta повторяет тесты, выдаёт `passed`, сохраняет проверяемый bundle и оставляет исходную ветку неизменной.

### 15.2 Нельзя объявить неуспех успехом

Агент сообщает «все проверки пройдены», но обязательный тест падает при независимом повторении. Результат — `failed`; ветка сохраняется, merge/push не происходит.

### 15.3 Нет evidence — нет passed

Повреждённый или отсутствующий обязательный report, неизвестный exit status и невозможность повторить проверку не дают `passed`.

### 15.4 Изоляция

Fixture пытается обратиться к host home, Docker socket, другому worktree и запрещённому сетевому адресу. Доступ блокируется, событие попадает в evidence, основная ветка и соседние запуски не изменяются.

### 15.5 Секреты

Тестовый secret canary передаётся только worker. После завершения его значение отсутствует в SQLite, обычных логах, API responses и EvidenceBundle. Эфемерные credential files удаляются при cleanup.

### 15.6 Отмена

Во время длительной команды пользователь выполняет cancel. После grace period контейнер остановлен, статус `cancelled`, доступные diff/logs сохранены, повторный scheduler tick не запускает задачу заново.

### 15.7 Перезапуск сервиса

Сервис принудительно завершается во время подготовки, выполнения и проверки. После старта reconciler не создаёт дубликатов, различает подтверждённые и неизвестные состояния и позволяет безопасно resume или cancel.

### 15.8 Равноправие интерфейсов

Один и тот же запуск можно создать через CLI, наблюдать в Web UI и отменить через CLI. Обе поверхности показывают одинаковые технический статус, verdict и evidence identifiers. Следующий этап повторяет этот сценарий через MCP и Agent Plugin без изменения доменных правил.

## 16. Стратегия тестирования

### 16.1 Unit и property tests

- reducer всех допустимых и запрещённых переходов Run;
- детерминированный расчёт Verdict;
- политика retries и approvals;
- path/network policy;
- сериализация и совместимость контрактов;
- хэширование и офлайн-проверка EvidenceBundle;
- redaction и обработка двоичных/больших логов.

### 16.2 Adapter contract tests

Один набор сценариев выполняется против каждого runtime адаптера: probe, start, structured events, approval, cancellation, resume и version mismatch. Адаптер не считается поддерживаемым при пропуске критических сценариев.

### 16.3 Fault injection

Обязательные сбои:

- агент зависает;
- CLI возвращает неизвестный формат;
- процесс исчезает без exit event;
- Docker переполняет memory/PID limit;
- тест превышает timeout;
- диск заканчивается во время записи evidence;
- SQLite недоступна при переходе состояния;
- сервис умирает после создания worktree, но до записи container id;
- сервис умирает после завершения команды, но до записи verdict;
- clock смещается назад;
- stale lease пытается завершить уже принадлежащий другому владельцу запуск;
- agent session указывает на другой worktree;
- повреждается manifest или отдельный артефакт.

Ожидаемое поведение для каждого сбоя — отсутствие ложного `passed`, отсутствие неучтённого дубликата и сохранение диагностики.

### 16.4 E2E и сравнительные запуски

Используются независимо созданные fixture-репозитории и повторяемые сценарии, а не скопированная реализация Auto-Claude. Один и тот же набор задач прогоняется минимум через два runtime. Сравниваются не только успехи, но и корректность отказов, recovery, сохранность evidence и неизменность основной ветки.

## 17. Наблюдаемость и эксплуатация

`verdicta doctor` проверяет:

- Node.js и поддерживаемую ОС;
- Docker daemon и возможность создать ограниченный контейнер;
- Git и поддержку worktree;
- доступность SQLite/artifact store;
- установленные agent CLI и их версии;
- поддерживаемый способ аутентификации;
- сетевые profiles;
- отсутствие незавершённых recovery conflicts.

Технические логи содержат correlation IDs и run/attempt identifiers, но не secrets. Диагностическая команда не изменяет состояние неявно: repair выполняется отдельной явной операцией.

## 18. Prior art и дифференциация

Verdicta не претендует на уникальность отдельных идей worktree isolation, evidence gates или agent orchestration. До реализации сравнительные сценарии должны включать следующие проекты.

### 18.1 Auto-Claude / Aperant

Auto-Claude служит исходным ориентиром по Kanban, спецификациям, Planner/Coder/QA и desktop-опыту. Текущий upstream развивается как Aperant под AGPL-3.0 и использует Electron с внешним coding-агентом. Verdicta — независимая Apache-2.0 реализация без копирования кода, prompt-файлов, схем хранения или дизайна интерфейса.

Главное отличие Verdicta — evidence-first control plane с независимым повторением проверок, отдельным доменным verdict, Docker workers и равноправными CLI/Web/MCP surfaces. Desktop и собственные ролевые agent workflows не входят в MVP.

Источники:
- https://github.com/AndyMik90/Aperant
- https://github.com/OBenner/Auto-Coding

### 18.2 Runproof

Runproof уже реализует близкую базовую модель: coding-agent или shell запускается в собственном worktree, результат принимается только после объявленных проверок, история хранится в SQLite, а merge не выполняется. Это обязательный prior art для Verdicta.

Целевое отличие Verdicta — постоянный восстанавливаемый service, Docker isolation, ACP/native/CLI capability model, расширенный EvidenceBundle, approvals, несколько клиентских surfaces и отдельная state machine recovery. Эти отличия являются требованиями к реализации, а не утверждением об их уникальности.

Источник: https://github.com/CAOShurong/runproof

### 18.3 Gatewright

Gatewright предоставляет evidence-gated work tracking, file-first события, live board, worktree runner, approvals/triage, resume, CLI и MCP. Поэтому Verdicta не должен позиционироваться как первый evidence-gated tracker или первый runner с worktree.

Фокус Verdicta — независимое повторное исполнение проверок после агента, content-addressed EvidenceBundle, Docker security boundary, детерминированный verdict, отделённый от технического статуса, и единый durable control plane для разных runtime адаптеров. В ходе реализации overlap повторно сравнивается на одинаковых E2E-сценариях.

Источник: https://libraries.io/npm/gatewright

### 18.4 eve

eve предоставляет composable agent/code extension модель и authenticated tooling. Verdicta выбирает другую границу: не собирает нового агента из расширений, а контролирует уже существующие coding-приложения через runtime адаптеры и независимо проверяет их результат.

Источник: https://eve.dev/docs/code-extension

## 19. Название и публикация

Рабочее и выбранное пользователем имя — **Verdicta**, CLI — `verdicta`.

Перед первым публичным релизом выполняется отдельная release-проверка npm package names, GitHub organization/repository, доменов и товарных знаков. Предварительный поиск GitHub не считается юридической проверкой доступности названия.

Первая публикация содержит Apache-2.0 license text и явное указание независимости от Auto-Claude/Aperant. Наличие ссылок на prior art не означает заимствование их кода или брендов.

## 20. Итоговые архитектурные решения

1. Исполняет код внешний coding-агент, а не Verdicta.
2. Ядру не нужен model API key; агент может требовать собственную аутентификацию.
3. Основной канал управления — `AgentRuntime` через ACP/native SDK/headless CLI.
4. MCP служит для знаний, инструментов и клиентского доступа к ядру, но не заменяет runtime control.
5. Агент получает `TaskContract`, а не поток микрокоманд.
6. Каждая попытка получает git worktree и Docker worker.
7. Verdicta независимо повторяет обязательные проверки.
8. `Run.status` и `Verdict` разделены.
9. Окончательный verdict вычисляется детерминированно; LLM не может перекрыть failed gate.
10. Результат — сохранённая локальная ветка, ChangeSet, EvidenceBundle и Verdict.
11. Автоматические merge/push запрещены в MVP.
12. Основной продукт — local service + CLI + Web UI; Agent Plugin и IDE extensions используют то же API позже.
13. Источник истины — SQLite и хэшированные файлы; JSONL является экспортом.
14. Проект независим и распространяется под Apache-2.0.
